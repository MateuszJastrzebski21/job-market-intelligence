# JMI Codebase Audit — 2026-05-18

**Status:** Draft for review — not committed.
**Scope:** Python backend (`src/jmi/`, `tests/`, configs). The `extension/` Chrome MV3 code and the 89 vitest tests were out of scope.
**Purpose:** Identify weaknesses in the Phase 1 + Phase 2 foundation before Phase 3 (RAG resume generator) is built on top.
**Repo state audited:** `main` HEAD `3fe5595`.

## Method

Four independent read-only sub-agents (Sonnet) audited the codebase:

1. **Security** — secrets, SQL injection, input validation, API-key handling, log hygiene.
2. **Test quality** — coverage, isolation, flake, fixtures, golden files.
3. **Observability + ops** — structlog, cost tracking, CLI UX, migration safety.
4. **Code smell + architecture** — ADR adherence, repository pattern, typing, cohesion, dead code.

This document synthesises their four reports into one prioritised issue list. The four reports
were delivered verbatim in the audit session transcript and can be appended here on request.

## One correction applied during synthesis

The architecture report recommends removing `"jjit"` from the `Source` literal, citing ADR-0008.
**This is incorrect.** ADR-0008 removed JJIT *server-side scraping*; ADR-0009 then re-introduced
JJIT as a *HITL Chrome-extension* source (ADR-0009 explicitly widened `Source` to include `jjit`;
PR5/PR14 implemented the JJIT content script; live JJIT postings exist in both databases).
**`"jjit"` is an active source and must stay.** The sub-agent was misled by a stale line in
`CLAUDE.md` — see issue **H6**. The genuinely-dead value is `"linkedin"` (see **M2**).

## Cross-cutting themes

- **Import-time side effects** — the DB engine and settings initialise at module import. Flagged independently by 3 of 4 agents. → C2
- **Ungraceful failure surfaces** — CLI commands dump raw tracebacks; `/api/health` reports `ok` while the DB is down. → H2
- **Test/eval infrastructure is not retrieval-ready** — no ranking metrics, no golden retrieval sets, ad-hoc fakes. → H5
- **Personal data is a new risk class** — Phase 3 ingests the user's real career history; today's log/storage/prompt discipline was designed for public job postings. → H1
- **Documentation drift actively misleads** — a stale `CLAUDE.md` line caused a wrong finding in this very audit. → H6

## Phase 3 readiness verdict

The architecture is sound and does **not** need a broad refactor. The separated pipeline
(ADR-0006), repository pattern, and Pydantic boundaries extend cleanly to a new "achievements"
domain. Phase 3 can proceed once the two Critical items are resolved (both are small, targeted
fixes — not large refactors) and the Phase 3 security prerequisites (H1) are designed into
PR-3.1 rather than retrofitted.

## Prioritised issue list

Each issue cites its file location and the source report (S = Security, T = Test quality,
O = Observability/ops, A = Architecture).

### Critical — resolve before Phase 3 work begins

**C1 — LLM refusal (`stop_reason`) never checked before `parsed_output` is consumed.**
`src/jmi/extractors/anthropic.py:82` · source A.
ADR-0005 explicitly warned a refusal can return non-conforming output. The extractor reads
`response.parsed_output` with no `stop_reason` guard; a refusal persists a malformed/empty
`JobExtract` silently. Phase 3 RAG retrieves `JobExtract` rows for CV-bullet generation —
silent corruption here degrades generated résumés invisibly.
*Fix:* guard on `response.stop_reason` before trusting `parsed_output`; skip + log on refusal.

**C2 — Database engine and settings initialise at module import time.**
`src/jmi/db/base.py:16-22` (`engine = _make_engine()` at import), `src/jmi/config.py:27`
(`get_settings()` uncached) · sources A, O, S (3 of 4 agents).
`engine` binds to whatever `DATABASE_URL` existed at import; tests and integration cannot
override it afterwards, and a missing `DATABASE_URL` crashes at import rather than at call
time. Phase 3 opens with PR-3.1 (achievement DB schema + Alembic migration), which needs
reliable DB integration testing.
*Fix:* lazy `get_engine()` accessor; `@lru_cache` on `get_settings()`; move the settings
read out of the import path.

### High — before the Phase 3 RAG MVP merges

**H1 — Phase 3 personal-data security prerequisites.** source S.
Phase 3 ingests the user's personal achievement files. Design into PR-3.1/3.2/3.4:
(a) sandbox all corpus file paths (`Path.resolve()` + `is_relative_to(ACHIEVEMENTS_DIR)`)
against traversal; (b) never log achievement content (title only); (c) store personal
embeddings in a separate, purgeable table, and keep DB backups out of git; (d) treat
job-posting text as untrusted input in prompts — indirect prompt injection — and add an
injection canary to the eval suite; (e) require auth on any Phase 3 retrieve/generate
endpoint. Cheap if planned, expensive to retrofit.

**H2 — CLI / health-check error handling is ungraceful.** source O.
Raw tracebacks on missing API key (`extractors/anthropic.py:50-53` + `cli.py:74`) and on
unreachable Postgres (`cli.py:54-78`); `analyze` catches only `ValueError` (`cli.py:158-167`);
`/api/health` returns `200 {"status":"ok"}` even when `db_ok=false` (`api/routes/health.py:13-15`).
*Fix:* friendly `try/except` in CLI command bodies; return HTTP 503 from `/api/health` when
the DB is down.

**H3 — Ingest API hardening.** source S.
`api/auth.py:19` — use `hmac.compare_digest` for timing-safe token comparison.
`api/schemas.py` — add `max_length`/`max_items` to batch lists and description strings
(unbounded payloads today). `config.py:18` — remove the hardcoded default DB password
(`jmi_dev_password`); fail loudly if `DATABASE_URL` is unset.

**H4 — Repository pattern is ambiguous.** `src/jmi/storage/base.py` · source A.
`AbstractRepository` is defined but unused; `evaluation/runner.py` uses its own inline
Protocols. Three approaches coexist. Phase 3 needs an `AchievementRepository` — decide the
canonical pattern (adopt or delete `AbstractRepository`) before adding it.

**H5 — Retrieval-evaluation infrastructure is absent.** source T.
The eval package measures *extraction* quality only — no recall@k / MRR / nDCG, no golden
retrieval sets, non-deterministic embeddings, and four ad-hoc fake-repo classes. Build
`evaluation/retrieval_metrics.py`, a `docs/ground_truth/rag_retrieval_seed.json` schema,
deterministic embedding fixtures, and a shared `tests/fakes.py`. Evaluation rigor is the
project's stated #1 differentiator — retrieval quality must be measurable from day one.

**H6 — Project docs are stale / self-contradictory.** source: main-session pre-audit.
`CLAUDE.md` "JustJoinIT: OFF the table" contradicts ADR-0009 (which brought JJIT back as a
HITL source). `CLAUDE.md` is loaded into every session's context and already caused a wrong
finding in this audit (the architecture agent's "remove jjit"). `docs/roadmap.md`
"Current state" still says Phase 2 is 0% / "PR18 pending" though it merged (#20). Trivial
edits, high leverage across all Phase 3 sessions.

**H7 — Phase 3 observability conventions not yet established.** source O.
No per-stage timing instrumentation, no embedding cost/duration tracking, eval runs are
ephemeral (stdout only — no history), no documented structlog event-naming convention, no
request-scoped context binding. Define these before the RAG modules are written so
instrumentation is built in, not retrofitted across 6 modules.
